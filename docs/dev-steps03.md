# デザイン改善フェーズ 開発手順（dev-steps03）

このドキュメントは、`firebase-sticky-board` の  
dev-steps02（認証・共有・権限・機能拡張）完了後に行う、  
**デザイン改善フェーズ**の作業手順メモです。

このフェーズでは、機能は増やしすぎず、  
**最小の作業量で「プロダクト感」と「操作の手応え」を整える**ことを目的とします。

## 次フェーズのゴール

このフェーズの到達点は以下です。

- ベースUIが「モダン/SaaS」寄りに統一されている
- 付箋は「カジュアル」な雰囲気（淡色・軽い影）を維持している
- 付箋操作にフィードフォワード/フィードバックがある（小さい範囲）
- Tailwind + shadcn/ui を導入し、UI基盤が整っている
- 既存のMVP/Phase02機能を壊さずに改善できている

## 基本方針（重要）

- UX改善は **付箋操作に限定**する（対象を増やしすぎない）
- スタイルは **ベース：SaaS / 付箋：カジュアル** とする
- UI部品の自作を避け、**shadcn/ui を必要分だけ使う**
- 既存の実装は壊さず、まずは **見た目の統一**を優先する
- フルデザイン刷新は行わない（1日1時間×1週間程度で収める）

## 対象範囲

### 改善対象（やる）

- Top画面（Card/ボタン/エラー表示の統一）
- Board画面（背景、ヘッダー導線、付箋のカード感）
- 付箋操作（ドラッグ、削除、色変更）の視認性と手応え
- 最低限のフォント設定（プロダクト感を出す）

### 対象外（やらない）

- ダークモード
- テーマ切り替え
- アニメーション多用
- 付箋回転
- 新機能（画像添付、サイズ変更、Undo/Redo等）
- 大規模なコンポーネント分割（必要最小限に留める）

## デザイン方針

### UX（小さい範囲）

#### フィードフォワード（操作前に分かる）

- 付箋がドラッグ可能（カーソル、hover）
- 削除できる（hoverで×が出る、アイコン）
- 色変更できる（色UIが「操作できる形」で見える）

#### フィードバック（操作中・操作後に手応え）

- ドラッグ中：shadow強化、z-index上昇
- 色変更：即時反映、選択色の強調
- 削除：反映が即時に見える（snapshot同期）

### スタイル（ベース：SaaS / 付箋：カジュアル）

#### ベース（SaaS）

- 背景：薄いグレー
- Surface：白（カード）
- Border：薄いグレー
- 角丸：8px
- shadow：弱め

#### 付箋（カジュアル）

- 淡色パレット（3〜4色）
- 軽い影
- 角丸：8px
- 回転なし（作業量削減）

## 技術選定

- Tailwind CSS
- shadcn/ui（Button / Input / Dialog / Card を中心に最小利用）

## 推奨する進め方（順番）

1. Tailwind 導入（既存inline styleからの移行準備）
2. shadcn/ui 導入（Button / Input / Card / Dialog）
3. 最低限のフォント設定（Inter + Noto Sans JP fallback）
4. Top画面の見た目統一（Card + ボタン + エラー）
5. Board画面の基礎スタイル（背景・余白・ボタン導線）
6. 付箋のカード感統一（余白・影・角丸・色）
7. 付箋操作UX（hover / drag中 / 削除表示 / 色選択）
8. 微調整（余白・整列・視認性）

## 開発手順

### 1. Tailwind 導入

目的：
- スタイルの統一と作業効率を上げる

実装：
- Tailwind を導入
- `index.css`（またはglobal css）に base を追加
- 既存の inline style を一部 `className` に置き換える準備をする

完了条件：
- Tailwind のクラスが反映される
- 画面表示が崩れていない

作業時メモ：
- Tailwind は v4 を使用
- shadcn/ui では v3 互換の tailwind.config.ts を併用する
- Tailwind の shadcn/ui 依存を次の工程で追加する予定
  - `pnpm add class-variance-authority clsx tailwind-merge lucide-react`

### 2. shadcn/ui 導入（最小）

目的：
- SaaS感のある基本UI（ボタン・入力・カード・ダイアログ）を短時間で揃える

実装：
- shadcn/ui を導入
- まず以下だけ使える状態にする：
  - Button
  - Input
  - Card
  - Dialog

完了条件：
- Button / Input を置換できる状態
- 依存追加が最小で収まっている

### 3. 最低限のフォント設定（プロダクト感）

目的：
- OS依存を減らし、最低限のプロダクト感を出す

方針：
- 英数：Inter
- 日本語：Noto Sans JP fallback（または system fallback）

実装：
- Google Fonts で Inter + Noto Sans JP を読み込む（最小ウェイト）
- Tailwind の `fontFamily.sans` を設定
- `body` に `font-sans` を適用

完了条件：
- 主要画面（Top/Board）でフォントが統一されている
- 文字が読みやすく、主張しすぎない

### 4. Top画面の見た目統一（SaaS）

目的：
- 入口画面で「プロダクト感」を出す

実装：
- 外枠を Card 化（余白・角丸・shadow）
- ボタンを shadcn Button に置換
- エラー表示を統一（小さめ、赤、余白整理）

完了条件：
- Top画面が整って見える
- ログイン導線が分かりやすい

### 5. Board画面の基礎スタイル（SaaS）

目的：
- ボード全体を「作業場」として整える

実装：
- 背景色を統一（薄グレー）
- 付箋追加ボタンを見やすい位置に固定（左上など）
- 余白とレイヤー（z-index）を整理

完了条件：
- ボード上のUIが邪魔にならない
- 付箋操作に集中できる

### 6. 付箋スタイルの統一（カジュアル）

目的：
- 付箋が「付箋っぽく」見え、読みやすい状態にする

実装：
- 付箋の padding / border / shadow / 角丸を統一
- 色パレットを 3〜4色に固定
- text の折返し（長文対策）を追加

完了条件：
- 付箋がカードとして綺麗に見える
- 色が調和している

### 7. 付箋操作UX（小さい範囲）

目的：
- フィードフォワード/フィードバックで「操作の手応え」を出す

実装（例）：
- hover：shadow強化、cursor: grab
- dragging：shadow強化、z-index上昇、cursor: grabbing
- 削除：hover時のみ表示（常時表示しない）
- 色変更：選択色の枠線強調、ボタンのhover

完了条件：
- 初見でも「掴める」「変えられる」「消せる」が伝わる
- 操作中に手応えがある

### 8. 微調整（必要最小限）

目的：
- 全体の統一感を仕上げる

実装：
- 余白のズレ調整
- ボタンサイズ、文字サイズの整理
- 画面のスクロールや端の見切れ確認

完了条件：
- UIが破綻していない
- “綺麗”に見える状態で止められている

## 補足：改善アイデア

- shadcn/uiの他のコンポーネント（ListやBadgeなど）が必要になった場合は、適宜サンプル的に導入を検討する

## 将来の検討のための補足

### 補足：より一般的な運用に寄せるための拡張方針

現状の共有リンク方式は「リンクを知っている人は編集できる」前提であり、MVP〜小規模用途では扱いやすい一方、公開範囲が広がるほどリスク（意図しない編集・荒らし等）が増えます。

次に「より一般的」な運用に寄せるなら、以下の順で段階的に強化するのが自然です。

1. Firestore security rules で「非匿名ログインのみボード作成」を必ず保証する
    - UI 側で弾くだけではなく、Rules 側でも create を拒否できる状態にする
2. 共有の強度を必要に応じて上げる
    - トークン方式（URL にランダムな editToken を含める / ボードに紐付ける）
    - 招待方式（メンバーコレクション、権限ロール、招待 UI）
3. 速度制限や簡単なスパム対策（Cloud Functions等）
    - Rulesで入力検証 + 更新フィールド制限 + 上限（付箋数など）
    - App Check を有効化（WebならreCAPTCHA系）
    - それでも必要なら、ボード作成（＋付箋作成）をFunctionsに寄せる

最初から強い共有モデル（招待・権限管理）を作り込むのではなく、必要になったタイミングで「共有の強度」を上げていく設計とする。

### 補足：リファクタリング方針

- 現状は「シングルファイルで完結・シンプルさ優先」。
- 以下の状態になったら、機能ごとに分割するリファクタリングを検討する：
  - 付箋（Note）の属性やUIが増えた時
  - 付箋追加フォームのロジックやデザインが複雑になる時
  - ボード系の状態管理・表示が肥大化する時
- 分割例：`<StickyNote />`コンポーネント、`NoteInput`フォーム、ドラッグ操作用のカスタムフックなど

※ ただし、過度な抽象化は避けること。

### 補足：認証まわりの検討

- Top画面のユーザー状態管理は、`auth.currentUser` への直接アクセスではなく、`onAuthStateChanged` を利用して state でユーザーを管理する方式に将来的に見直すとよい。
  - 理由：画面初期化時や認証フローの非同期切り替えに強くなるため。
- ログアウト機能については、現状のフロー・要件では未実装だが、必要に応じて`signOut(auth)`で対応可能。
- ルーティング対応、ボード作成フローの動作確認後に検討
